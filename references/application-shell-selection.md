# 应用形态与系统外壳选择

先判断产品需要“聚焦单页面”还是“完整系统外壳”，再选择页面模式和组件。不要把工程封装与界面形态混为一谈。

## 三个独立维度

| 维度 | 典型选择 | 说明 |
|---|---|---|
| 交付封装 | 单 HTML / 多文件工程 | 单 HTML 也可以包含完整系统外壳 |
| 前端架构 | SPA / MPA / 静态页面 | SPA 可以有多路由、侧栏和全局状态 |
| 产品外壳 | 聚焦单页面 / 系统应用 | 本文件主要判断这一维度 |

用户说“单页应用”时，结合上下文确认他指的是单文件、SPA 技术架构，还是没有全局导航的聚焦页面；不要自行把三者视为同义词。

## 判定顺序

1. **已有产品优先**：仓库已有导航、路由、用户区或布局组件时，把新页面嵌入现有外壳，除非用户明确要求独立页面。
2. **明确要求优先**：用户明确说“不要导航”“嵌入页”“完整后台”“带用户信息”等时直接遵循。
3. **按需求信号判断**：证据明显时直接选择，并在交付中说明一句。
4. **证据不足时让用户选择**：外壳会显著影响布局、信息架构和实现范围，实施前给出两个明确选项。

不要只因为业务属于“后台”就机械添加侧栏，也不要为了让页面看起来完整而虚构无关模块。

以下表述本身都不足以直接选择系统应用：

- “做一个客户运营分析页面”
- “生成一个风控看板”
- “设计 CRM 客户详情”
- “输出一个 HTML 页面”

它们既可能是独立页面，也可能是现有系统内页。没有仓库外壳、多个全局模块、用户/权限/组织或明确独立交付信号时，必须提供选择。

## 聚焦单页面

优先选择聚焦单页面的信号：

- 单一、闭环任务，例如查看一张关系图、填写一次表单、运行一个分析工具。
- 独立 Demo、概念验证、公开查询页、活动页或准备嵌入其他系统的模块。
- 用户明确要求无全局导航、无账号区或只展示核心内容。
- 没有跨模块跳转、角色切换、全局通知或系统级设置。

默认结构：

```text
页面级标题 / 必要上下文 / 主要操作
局部筛选或工具栏
核心工作区
局部详情、状态和反馈
```

- 不伪造侧栏、全局通知、环境切换和用户头像。
- 需要返回宿主系统时提供清楚的返回入口或嵌入协议。
- 单页仍要处理加载、空态、失败、权限和窄屏降级。

## 系统应用

优先选择系统应用的信号：

- 有多个稳定业务模块、对象类型或跨页面任务。
- 存在角色、权限、组织、环境、消息、审计或全局搜索。
- 用户需要导航定位、面包屑、账号操作、工作区切换或模块间跳转。
- 用户明确请求完整中后台、运营平台、CRM 系统、风控系统、数据平台或管理门户，而非只说其中一个页面。

默认外壳：

```text
左侧导航：产品标识、模块分组、当前项、系统设置
顶部栏：折叠、全局上下文、环境、通知、帮助、用户信息
内容区：面包屑、页面标题、操作、筛选、主工作区
```

- 导航项必须来自真实或合理推导的业务信息架构。
- 用户信息、权限与环境状态要与任务有关，不用装饰性假数据喧宾夺主。
- 只实现一个页面时，其余导航可以作为明确标注的演示入口，但不能伪装成已完成模块。
- 已有系统外壳时复用其尺寸、组件、路由和权限规则。

## 证据不足时的选择提示

实施前用简短、互斥的选择说明：

> 这个需求可以做成两种形态：  
> 1. 聚焦单页面：不带全局导航，适合独立 Demo、嵌入页或单一工具。  
> 2. 完整系统页面：带侧栏、顶栏、用户信息和面包屑，适合作为中后台产品模块。  
> 你希望采用哪一种？

如果用户要求立即执行、不便等待选择，则根据主要任务和现有仓库做最小假设；在交付中明确所选形态以及另一种形态可如何升级。

## 验收

- 外壳选择有需求证据，不依赖“看起来更像产品”的主观判断。
- 单页面没有无关全局组件；系统应用包含稳定导航与全局上下文。
- 交付封装、前端架构和产品外壳分别说明，没有概念混用。
- 主题切换不改变应用形态、信息架构和主任务位置。
