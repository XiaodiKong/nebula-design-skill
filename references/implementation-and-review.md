## 实现策略

1. 先检查现有框架、组件库、设计令牌和页面模式。
2. 优先复用现有基础组件，再封装业务组件。
3. 将选中主题映射为 `--admin-*` 语义令牌，不在组件中散落十六进制色值。
4. 先实现主任务闭环，再补完整状态和边界。
5. 使用真实中文业务文案和具有差异性的样例数据。
6. 保留接口边界；Mock 数据与请求层分离，方便替换。

新项目且用户未指定栈时，可选择 React + TypeScript + Vite；样式优先使用 CSS 变量和项目已有方案。不要为了应用此设计系统强制替换成熟组件库。

## 代码约束

- 使用语义 HTML；按钮使用 `button`，导航使用 `nav`，表格数据使用正确表格结构。
- 组件职责清晰：页面编排、业务组件、基础组件和数据访问分离。
- 用语义属性表示状态，如 `data-state`、`aria-selected`，避免依赖脆弱 DOM 层级。
- 交互状态由数据驱动，不把状态文案复制到多个条件分支。
- 表单字段提供稳定名称、标签、错误和帮助关系。
- 避免纯视觉占位；Skeleton 的结构应接近最终内容。
- 不引入只为一个小效果服务的大依赖。
- 遵守仓库格式、类型、Lint 和测试约定。

## 数据与状态

定义状态模型，而不是散落布尔值：

```ts
type AsyncState<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: T; updatedAt: string }
  | { status: "empty" }
  | { status: "error"; message: string; retryable: boolean };
```

实现时覆盖：

- 初次加载与局部刷新。
- 空数据和筛选无结果。
- 可重试与不可重试错误。
- 乐观更新的回滚。
- 未保存变更。
- 权限不足和只读。
- 并发修改或版本冲突。
- 长任务的进度和后台执行。

不要用 `0`、空字符串和 `null` 表示同一个业务含义。金额、时间、百分比和时区必须格式化并明确单位。

## 响应式与性能

- 从目标用户的常见桌面尺寸开始验证，至少覆盖约 1440px 和 1024px 宽度。
- 表格使用列优先级、固定列和横向滚动，不机械转换为卡片。
- 窄屏隐藏装饰性或低优先级信息，保留对象、状态和主操作。
- 长列表使用分页或虚拟化；搜索、筛选请求需要防抖或取消过期请求。
- 图表和编辑器按需加载；避免首屏加载所有详情面板。
- 保持布局稳定，加载和按钮反馈不引起明显跳动。

## 验证流程

代码交付前执行：

1. 运行仓库已有的格式、Lint、类型检查和测试。
2. 启动页面并走通主流程。
3. 检查加载、空、无结果、失败、无权限和长内容。
4. 检查键盘导航、焦点、标签关联和对比度。
5. 检查至少两个目标宽度下的溢出与遮挡。
6. 检查浏览器控制台错误和重复请求。
7. 对照以下评审量表，修复高影响问题。
8. 修改主题、令牌或 Demo 时运行：

```bash
node scripts/validate-theme-contract.mjs
node scripts/validate-demo.mjs
```

无法执行某项验证时明确说明原因，不要声称已验证。

## 设计评审量表

每项按 `0–2` 评分：

| 维度 | 0 | 1 | 2 |
|---|---|---|---|
| 任务清晰度 | 主任务不明 | 可推断 | 入口和结果明确 |
| 信息层级 | 平铺或混乱 | 基本分组 | 阅读与操作顺序清楚 |
| 操作效率 | 跳转/确认过多 | 可完成 | 高频路径短且保留上下文 |
| 数据表达 | 缺单位/口径 | 大体可读 | 格式、口径、时间完整 |
| 状态完整性 | 仅静态成功态 | 覆盖部分 | 异常、权限和边界完整 |
| 视觉一致性 | 样式散乱 | 局部一致 | 令牌、密度、组件统一 |
| 可访问性 | 键盘或标签缺失 | 基本可用 | 焦点、语义、对比完整 |
| 响应式 | 明显溢出 | 简单适配 | 按任务优先级合理降级 |
| 风险控制 | 危险操作不清 | 有确认 | 后果、范围、撤销/审计完整 |
| AI 可控性 | 黑盒自动执行 | 可审阅 | 来源、差异、确认和回退完整 |

优先修复得分为 0 且影响主流程、数据安全或可访问性的项目。不要为了提高视觉分数牺牲任务效率。

评审输出格式：

```text
[优先级] 位置 — 问题
影响：用户会遇到什么阻力或风险
建议：具体改成什么
```
